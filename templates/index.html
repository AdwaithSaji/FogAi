FogAI — Low-Latency Intelligent IoT Architecture
Final Year Project  ·  Industry 5.0 / Smart Manufacturing  ·  Edge AI & Fog Computing
PROJECT OVERVIEW

FogAI is an intelligent IoT architecture designed for real-time industrial monitoring and control. It solves a fundamental problem in modern smart manufacturing: traditional cloud-based systems are too slow and too fragile for safety-critical decisions. By embedding a lightweight AI decision engine directly at the fog layer — between the sensors and the cloud — FogAI makes intelligent decisions in under 5 milliseconds, even when the internet is completely unavailable.

This project simulates a CNC industrial machine (CNC-MACHINE-07) continuously monitored by five sensor parameters. A fog node (FOG-NODE-001) processes every reading locally using a two-stage AI engine — hard safety rules and a continuous weighted risk score — and decides in real time whether to act locally, sync to the cloud, or both. The live dashboard you see above is the actual system running and making decisions cycle by cycle.

The Problem We Solve

Cloud-based IoT systems route every sensor reading to a remote server before acting. This creates:


  • 100–300 ms latency on every decision cycle
  • Complete system failure when network drops
  • High bandwidth usage for routine data
  • No local intelligence — the machine cannot protect itself

In a CNC machine running at high speed, a 200 ms response to an overheating event is the difference between a safe stop and a fire. Traditional architectures cannot meet this requirement.

Our Fog AI Solution

We place a Fog Node — a compute unit — directly beside the equipment. It runs our AI engine continuously:


  • Reads 5 sensor streams every 750 ms
  • Runs feature extraction and normalisation
  • Evaluates 5 hard safety rules (R1–R5)
  • Computes a weighted risk score (0.0–1.0)
  • Triggers local actions in < 5 ms
  • Forwards only necessary data to cloud
  • Operates fully offline during network failure
  • Logs all decisions locally + to cloud

The cloud receives structured telemetry for long-term trend analysis and storage — but is never in the critical decision path.

AI Decision Engine

Two-layer intelligence model:

LAYER 1 — HARD SAFETY RULES (highest priority)

RuleConditionAction
R1Temp ≥ 90°CSHUTDOWN
R2Temp ≥ 75°CALERT
R3Network downFog-only mode
R4Vibration ≥ 4gSHUTDOWN
R5CPU ≥ 95%Throttle

LAYER 2 — WEIGHTED RISK SCORE

ScoreRouting
< 0.35Cloud sync (low risk)
0.35–0.65Fog only (medium)
> 0.65Alert — Fog + Cloud
WHAT WE BUILT — SYSTEM COMPONENTS
sensor.py
IoT sensor simulator. Generates realistic temperature, CPU load, vibration, humidity, and network readings with Gaussian noise, gradual drift, and 7 scripted anomaly events injected at precise cycles.
ai_engine.py
The core intelligence. Feature extraction → rule evaluation → weighted risk scoring → routing decision. Outputs destination (FOG/CLOUD/BOTH), action, risk score, and confidence. Designed for <1 MB RAM footprint.
fog_node.py
Orchestrates one full sensor cycle: receive reading → AI decision → execute local action (shutdown, alert, throttle) → optionally forward to cloud. Writes structured JSONL logs locally.
web_app.py
Flask server streaming live simulation data to this dashboard via Server-Sent Events (SSE). Every 750 ms a real decision is computed and pushed to the browser in real time — no page refresh needed.
SIMULATION WALKTHROUGH — 60 CYCLES
Phase 1 · Cycles 1–21 · Normal Operation
Machine runs normally. Risk scores stay below 0.45. Low-risk readings are forwarded to the cloud for storage. Fog routes based on current network quality. You can observe the routing switching between FOG and CLOUD in real time on the architecture diagram.
Phase 2 · Cycles 22–32 · Network Failure
Network starts degrading at cycle 22. By cycle 27, latency exceeds 9999 ms — network is offline. Rule R3 fires. The fog node switches to fully autonomous mode, processing and acting without any cloud connectivity. The cloud box in the diagram dims to show it is unreachable.
Phase 3 · Cycles 33–57 · Crisis Event
Overheating begins at cycle 33 — temperature climbs past 90°C, triggering Rule R1 (EMERGENCY SHUTDOWN) with response in under 4 ms. At cycle 38, a vibration shock triggers Rule R4. The machine is offline and network is also down — fog handles everything alone. This is the core value of the architecture.
Phase 4 · Cycles 58–60 · Recovery
The fault is cleared at cycle 58. Temperature drops, network recovers. The system normalises automatically — no manual reset needed. Cloud sync resumes for long-term trend analytics. The fog node transitions back to normal routing based on current risk scores.
